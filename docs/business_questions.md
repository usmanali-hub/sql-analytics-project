## 1. Which countries generate the most revenue?

Single-table aggregation on Invoice. Average invoice value shows whether a country wins on volume or on basket size.

```sql

       COUNT(*)                     AS invoices,
       ROUND(SUM(Total), 2)         AS revenue,
```

## 2. Who are the 10 highest-spending customers?

INNER JOIN Customer to Invoice. Every invoice has a customer (the foreign key is NOT NULL), so no rows are lost.

```sql

       c.FirstName || ' ' || c.LastName AS customer,
       c.Country,
       COUNT(i.InvoiceId)               AS invoices,
       ROUND(SUM(i.Total), 2)           AS lifetime_spend
FROM Customer AS c
JOIN Invoice  AS i ON i.CustomerId = c.CustomerId
GROUP BY c.CustomerId, c.FirstName, c.LastName, c.Country
```

## 3. Which genres earn the most, and how much revenue has no genre?

Genre is a nullable foreign key on Track, so an INNER JOIN to Genre would silently drop untagged tracks. LEFT JOIN plus COALESCE keeps them visible as 'Unknown'. (In this database every track has a genre, so 'Unknown' never appears, but the schema allows it.)

```sql
SELECT COALESCE(g.Name, 'Unknown')            AS genre,
       SUM(il.Quantity)                       AS units_sold,
       ROUND(SUM(il.UnitPrice * il.Quantity), 2) AS revenue
FROM InvoiceLine AS il
JOIN Track       AS t ON t.TrackId = il.TrackId
LEFT JOIN Genre  AS g ON g.GenreId = t.GenreId
GROUP BY genre
ORDER BY revenue DESC, genre
LIMIT 10;
```

## 4. Which 10 artists bring in the most revenue?

Four-table join chain InvoiceLine -> Track -> Album -> Artist. Album.ArtistId is NOT NULL, but Track.AlbumId is nullable; tracks without an album would be excluded by the inner join. (In this database none are, which a test confirms by reconciling to total revenue.)

```sql
SELECT ar.Name                                AS artist,
       COUNT(DISTINCT t.TrackId)              AS tracks_sold,
       ROUND(SUM(il.UnitPrice * il.Quantity), 2) AS revenue
FROM InvoiceLine AS il
JOIN Track  AS t  ON t.TrackId  = il.TrackId
JOIN Album  AS al ON al.AlbumId = t.AlbumId
JOIN Artist AS ar ON ar.ArtistId = al.ArtistId
GROUP BY ar.ArtistId, ar.Name
ORDER BY revenue DESC, artist
LIMIT 10;
```

## 5. How does revenue move month by month?


## 6. How much revenue does each support representative's customer base generate?

Employee -> Customer -> Invoice. LEFT JOINs keep employees with no customers (managers) in the output with zero instead of dropping them.

```sql
       e.Title,
       COUNT(DISTINCT c.CustomerId)      AS customers,
       COUNT(i.InvoiceId)                AS invoices,
       ROUND(COALESCE(SUM(i.Total), 0), 2) AS revenue

LEFT JOIN Customer AS c ON c.SupportRepId = e.EmployeeId
LEFT JOIN Invoice  AS i ON i.CustomerId   = c.CustomerId
```

## 8. How many customers have placed 1, 2, 3... invoices?

Aggregate of an aggregate: count invoices per customer in a subquery, then count customers per invoice count. A customer with no invoices would appear as 0 because of the LEFT JOIN.

```sql
SELECT invoice_count,
       COUNT(*) AS customers
FROM (
    SELECT c.CustomerId, COUNT(i.InvoiceId) AS invoice_count
    FROM Customer AS c
    LEFT JOIN Invoice AS i ON i.CustomerId = c.CustomerId
    GROUP BY c.CustomerId
)
GROUP BY invoice_count
ORDER BY invoice_count;
```

|---|---|
| 6 | 1 |
| 7 | 58 |

## 10. Who reports to whom, and how many direct reports does each manager have?

A self-join: Employee joined to itself on ReportsTo. The top of the tree has ReportsTo NULL, so the manager side must be a LEFT JOIN or that person disappears.

```sql
SELECT e.EmployeeId,
       e.FirstName || ' ' || e.LastName                AS employee,
       COALESCE(m.FirstName || ' ' || m.LastName, '(none: top of the tree)') AS manager,
```

## 11. How concentrated is revenue across customers, split into spend quartiles?

A CTE totals spend per customer, NTILE(4) ranks customers into quartiles (1 = biggest spenders), and the outer query sums each quartile. 59 customers do not divide evenly by 4, so the first quartiles hold 15 customers and the last two hold 14.

```sql
WITH customer_spend AS (
    SELECT CustomerId, SUM(Total) AS spend
    FROM Invoice
    GROUP BY CustomerId
),
ranked AS (
    SELECT CustomerId, spend,
           NTILE(4) OVER (ORDER BY spend DESC, CustomerId) AS quartile
    FROM customer_spend
)
SELECT quartile,
       COUNT(*)                                          AS customers,
       ROUND(SUM(spend), 2)                              AS revenue,
       ROUND(100.0 * SUM(spend) / (SELECT SUM(spend) FROM customer_spend), 1) AS pct_of_revenue
FROM ranked
GROUP BY quartile
ORDER BY quartile;
```

| quartile | customers | revenue | pct_of_revenue |
|---|---|---|---|
| 1 | 15 | 654.3 | 28.1 |
| 2 | 15 | 584.3 | 25.1 |
| 3 | 15 | 564.3 | 24.2 |
| 4 | 14 | 525.7 | 22.6 |

## 12. How does revenue change year over year, and what is the running total?

Yearly rather than monthly buckets on purpose: monthly revenue in this database is almost flat, so a month-on-month change would be a column of zeros. SUM() OVER an ordered frame gives the running total; LAG() fetches the previous year in the same row so the percentage change needs no self-join. The first year has no predecessor, so its change is NULL rather than an invented zero. The year is the first four characters of the timestamp text, which works the same in SQLite, DuckDB and PostgreSQL.

```sql
WITH yearly AS (
    SELECT SUBSTR(CAST(InvoiceDate AS VARCHAR), 1, 4) AS year,
           COUNT(*)                                    AS invoices,
           SUM(Total)                                  AS revenue
    FROM Invoice
    GROUP BY SUBSTR(CAST(InvoiceDate AS VARCHAR), 1, 4)
)
SELECT year,
       invoices,
       ROUND(revenue, 2)                                                          AS revenue,
       ROUND(SUM(revenue) OVER (ORDER BY year), 2)                                AS cumulative_revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY year))
             / LAG(revenue) OVER (ORDER BY year), 1)                              AS pct_change_vs_previous_year
FROM yearly
ORDER BY year;
```

| year | invoices | revenue | cumulative_revenue | pct_change_vs_previous_year |
|---|---|---|---|---|
| 2021 | 83 | 449.46 | 449.46 |  |
| 2022 | 83 | 481.45 | 930.91 | 7.1 |
| 2023 | 83 | 469.58 | 1400.49 | -2.5 |
| 2024 | 83 | 477.53 | 1878.02 | 1.7 |
| 2025 | 80 | 450.58 | 2328.6 | -5.6 |

## 13. Who are the top 2 artists in each of the five biggest genres?

Top-N per group: ROW_NUMBER() restarts for every genre (PARTITION BY) and the outer query keeps rows 1 and 2. Ties are broken by artist name so the result is stable. Artists rather than tracks are ranked on purpose: no track in this database sold more than twice, so a per-track ranking would be a wall of ties. The five genres come from a second CTE.

```sql
WITH artist_genre_revenue AS (
    SELECT g.GenreId, g.Name AS genre, ar.ArtistId, ar.Name AS artist,
           SUM(il.UnitPrice * il.Quantity) AS revenue
    FROM InvoiceLine AS il
    JOIN Track  AS t  ON t.TrackId  = il.TrackId
    JOIN Genre  AS g  ON g.GenreId  = t.GenreId
    JOIN Album  AS al ON al.AlbumId = t.AlbumId
    JOIN Artist AS ar ON ar.ArtistId = al.ArtistId
    GROUP BY g.GenreId, g.Name, ar.ArtistId, ar.Name
),
top_genres AS (
    SELECT GenreId
    FROM artist_genre_revenue
    GROUP BY GenreId
    ORDER BY SUM(revenue) DESC, GenreId
    LIMIT 5
),
numbered AS (
    SELECT genre, artist, revenue,
           ROW_NUMBER() OVER (PARTITION BY GenreId ORDER BY revenue DESC, artist) AS rn
    FROM artist_genre_revenue
    WHERE GenreId IN (SELECT GenreId FROM top_genres)
)
SELECT genre, rn AS rank_in_genre, artist, ROUND(revenue, 2) AS revenue
FROM numbered
WHERE rn <= 2
ORDER BY genre, rn;
```

## 14. Who is the biggest-spending customer in each country with more than one customer?

RANK() (not ROW_NUMBER) is used on purpose: if two customers tie for first in a country both are returned instead of one being dropped arbitrarily. COUNT() OVER a partition supplies the country's customer count without a second aggregation. Spend is rounded to cents before ranking because summed floating-point values can differ in the last bit between engines and silently break a tie (this was caught by the DuckDB portability test).

```sql
WITH customer_spend AS (
    SELECT c.CustomerId,
           c.FirstName || ' ' || c.LastName AS customer,
           c.Country,
           ROUND(SUM(i.Total), 2) AS spend
    FROM Customer AS c
    JOIN Invoice  AS i ON i.CustomerId = c.CustomerId
    GROUP BY c.CustomerId, c.FirstName, c.LastName, c.Country
),
ranked AS (
    SELECT Country, customer, spend,
           RANK()  OVER (PARTITION BY Country ORDER BY spend DESC) AS spend_rank,
           COUNT(*) OVER (PARTITION BY Country)                    AS customers_in_country
    FROM customer_spend
)
SELECT Country, customer, spend, customers_in_country
FROM ranked
WHERE spend_rank = 1 AND customers_in_country > 1
ORDER BY customers_in_country DESC, Country, customer;
```

## 15. How many genres does it take to reach 80% of revenue?

A Pareto table. Genres are ordered by revenue and a running SUM() OVER divides by the grand total to give the cumulative share. The ROWS frame is explicit: the default RANGE frame would treat genres with equal revenue as one block and jump the running total. The answer is the first row at or above 80%.

```sql
WITH genre_revenue AS (
    SELECT g.Name AS genre, SUM(il.UnitPrice * il.Quantity) AS revenue
    FROM InvoiceLine AS il
    JOIN Track AS t ON t.TrackId = il.TrackId
    JOIN Genre AS g ON g.GenreId = t.GenreId
    GROUP BY g.GenreId, g.Name
)
SELECT genre,
       ROUND(revenue, 2) AS revenue,
       ROUND(100.0 * SUM(revenue) OVER (ORDER BY revenue DESC, genre
                                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
             / SUM(revenue) OVER (), 1) AS cumulative_pct
FROM genre_revenue
ORDER BY revenue DESC, genre;
```
